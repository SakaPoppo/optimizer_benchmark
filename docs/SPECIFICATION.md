# Optimizer Benchmark 仕様書

- バージョン：v0.2（基本仕様・実装前）
- 対象：Ns Shift の FastAPI / OR-Tools 製 optimizerAPI
- 用途：開発者向けローカル計測・品質評価・バージョン比較
- ステータス：**確定**＝会話で採用、**暫定**＝検証が必要、**未決定**＝今後定義

## 1. 目的・基本方針【確定】
optimizerAPI のコード・探索設定を変更した際、**処理速度だけでなく生成の成否・制約・品質・ばらつき**を同一データセットで比較し、退行を発見する。
- 最終方針はアルゴリズム評価＋API負荷評価（C）。初期開発はアルゴリズム評価（A）のみ。
- 初期はローカルの開発者向けツール。Cloud Run の並列・負荷試験は将来拡張。
- 旧 API を再起動しなくても、過去に保存した**測定結果のスナップショット**と比較できる方式。接続先 API URL は切替可能。

## 2. 技術構成【確定】
- Python / Streamlit：実行画面・分析・レポート・比較
- httpx：optimizerAPIへの HTTP リクエスト
- SQLite：バージョン、ケース、試行、計測値などの履歴
- JSONファイル：テスト入力と生成されたシフト（原本を保存）
- psutil 等：ローカル API プロセスの CPU / メモリを計測する将来の手段（正確な方式は暫定）
- Runner を Streamlit UI から分離し、CLIからも実行可能にする。

## 3. 計測の役割分担【確定】
### 3.1 API側
- 生成した `shifts`、`solver_status`、`phase_results`、`issues` を返す（現行APIに存在）。
- 各フェーズのソルバー探索時間・ステータス・統計は API 内で計測し、ベンチマーク用に取得できるよう拡張する（**実装方法は暫定**）。
- 通常の `/generate` の互換性を維持し、無断でレスポンスや認証を壊さない。
### 3.2 Benchmark側
- HTTP の送信からレスポンス受信完了までの所要時間、HTTPエラー、接続失敗を記録。
- **入力条件と完成シフトから独立した品質評価器**で制約・偏り・連勤を計算。APIのissuesは別に記録。
- 全体の成功率、タイムアウト率、平均・中央値・p95、繰り返し試行のばらつきを集計。
- CPU・メモリは実測可能な環境でのみ記録。欠損値は未計測と表示。

## 4. テストケース【人数・パターン・回数は確定、具体値は暫定】
### 4.1 16ケース
人数は10・20・30・40人。各人数について以下の4パターンを用意する。
- A `baseline`：追加の希望休なし（前月引継ぎ・基本の曜日固定休は別扱い）。
- B `random_requests`：1人当たり月約2日、seed固定の希望休。
- C `fixed_assignments`：Bに加え一部の日勤・夜勤・休みなどを固定。
- D `stress`：1人当たり月3〜4日程度、一部の日に希望休集中。意図的な解なしは初期セットに混ぜない。

### 4.2 実行モード【確定】
| モード | 16ケース当たり試行回数 | 合計 |
|---|---:|---:|
| Quick | 各1回 | 16回 |
| Standard | 各3回 | 48回 |
| Full | 各10回 | 160回 |

基本は逐次実行。1試行ごとに保存し、中断後は未完了分から再開する。

### 4.3 Ns Shift Trial データを参照【実コード確認済み、比率適用は暫定】
参照先：`SakaPoppo/NS_shift` の `shifts/trial/data.py` と `shifts/trial/context.py`。
- デモ20人：必要日勤7人（35%）、必要夜勤3人（15%）、必要日別リーダー1人（5%）
- リーダー役割者9人（45%）、夜勤可能者20人（100%）
- 能力分布：Lv5=2人（10%）、Lv4=4人（20%）、Lv3=5人（25%）、Lv2=5人（25%）、Lv1=4人（20%）
- 月休日数：通常10日（28日月は9日）、最大連勤5日、夜勤明け翌日休のルールあり
- デモは3人に曜日固定休、前月から夜勤3人・明け3人の引継ぎがある。

**スタッフ数で変動する日勤・夜勤・役割・能力構成はデモの比率を出発点とする。** 丸め方は暫定（案：日勤は四捨五入、夜勤は切り捨て、役割者は四捨五入）。10人などで不成立になり得るため、最終的な人数は成立性検証後に**固定されたテストデータ**として保存する。測定中に自動調整しない。日別必須リーダー数はデモでは1人だが、人数比例の丸めを安易にそのまま適用しない。

共通条件：同じ人数なら希望休パターン間でスタッフ構成・勤務基本条件を共通にする。対象月・日数を固定し、シード、元データと JSON ハッシュ、データセット世代を保存する。対象月は例として30日月とし、**実際の年月・境界条件の確定は未決定**。

### 4.4 成立性確認【確定】
予定勤務枠と休日・夜勤明け・人数制約が矛盾しないか事前検査する。実際の解存在は事前ソルバー検証を経て固定。`422` / infeasible は通常の品質スコアとして扱わず、原因別に集計する。

## 5. 収集する測定値
### 5.1 処理性能【確定：対象、暫定：採取実装】
- HTTP応答時間、API内部の入力正規化・モデル構築・各フェーズ・結果変換の時間
- フェーズ名、status、optimal、objective_value、時間上限、実時間、best bound、branch数、conflict数、採用解の有無
- CPU使用率/CPU時間、ピークメモリ、時間切れ（クライアント側とソルバー探索時間上限を区別）
- 環境：CPU数、メモリ、OS、Python/OR-Tools、ワーカー数、各フェーズ時間上限、可能ならソルバーseed

### 5.2 生成成否・制約【確定】
- HTTP成功と**生成成功**と**最適性証明**を区別する。
- `OPTIMAL` / `FEASIBLE` / `UNKNOWN` / `INFEASIBLE` / `NOT_RUN` をフェーズ別に記録。
- ハード制約違反、セミハード制約違反を項目別件数・影響日・影響スタッフとともに残す。
- 違反評価は独立評価器で計算。API `issues` は元のコード・severity・詳細として別保存。

### 5.3 生成品質【確定：指標、暫定：正確な算式】
- 日勤：日別人数、必要人数からの差、人数の最頻値との差が2人以上の日数
- 夜勤：スタッフごとの夜勤回数、対象者間の最大最小差、標準偏差
- 能力：日勤・夜勤別の日次能力合計と期待値、偏差率（夜勤は夜勤可能者を母集団にする）
- 連勤：最大連勤数、上限超過、長期連勤の分布（前月引継ぎを考慮）
- 公平性：勤務区分別回数の分布、休日数の差
- 総合点は当初作らず、指標別に表示する。
- **評価器バージョン**を保存し、評価式変更後でも元JSONから過去のシフトを再評価できるようにする。

### 5.4 再現性・安定性【確定】
- 同一入力を各モードの回数だけ実行し、生成成功率、時間の中央値・分散・p95、品質のばらつきを記録。
- 乱数seed、worker数、探索上限を保存。seed固定でも完全に同一結果になるとは限らない。
- p95は小標本では不安定なので、試行数を必ず併記する。

## 6. バージョン管理【確定】
- バージョン名・変更概要を手入力可能とする。
- GitコミットSHA、未コミット変更、API・Python・OR-Toolsバージョンなどは取得可能なら自動記録。
- ローカルのGit SHAと**実際に動いている API プロセスのコード一致**は区別する。リモート環境はデプロイ時のSHAをAPIから返す仕組みを将来整備する。
- 1バージョンに複数 benchmark_run を紐づけ、結果を上書きしない。
- 比較は保存済みの結果を読み込み、旧APIを起動し直さない。

## 7. UIとレポート【確定】
画面：①ベンチマーク実行、②結果分析、③バージョン比較、④履歴・バージョン別レポート。
- 設定：API URL、バージョン名、変更概要、モード、進捗、停止・再開。
- レポート：実行日時・コード/環境/データセット情報、生成成功率、処理時間、フェーズ別、制約違反、日勤夜勤と能力・連勤の品質グラフ、個別ケース、元シフトの閲覧。
- 比較：ベースライン / 対象バージョンを選び、同一ケース同士の性能・品質変化を表示。条件違いは警告する。
- レポートHTML/PDFエクスポートは**将来候補**（初期必須ではない）。

## 8. 保存構造【暫定：概念設計】
SQLite初期案の8テーブル：
1. `api_versions`：バージョン名、変更概要、SHAなど
2. `datasets`：固定データセット世代、ハッシュ
3. `benchmark_cases`：人数・パターン・入力ファイル参照
4. `benchmark_runs`：1バージョンの1回の一括測定・環境・モード・状態
5. `benchmark_trials`：個別HTTP実行の成否・時間・成果物パス
6. `phase_metrics`：各フェーズの状態・時間・探索統計
7. `quality_metrics`：試行の評価指標（評価器バージョン付き）
8. `constraint_violations`：独立評価の制約違反

正規化、カラム型、インデックス、ファイル命名、APIのissuesの保存形式は実装前に詳細化する。JSONは相対パスとハッシュをDBで参照する。

## 9. 実行信頼性【確定】
- 逐次実行を基本とし、1試行ごとに結果永続化。
- 実行の状態：pending / running / completed / interrupted などを管理。生成失敗も試行が完了した事実として保存。
- 再開では未完了試行のみ再試行。HTTP/ソルバー/接続の失敗理由を識別。
- API同時リクエストを無制限に送らない。本番APIの認証・費用・利用制限を尊重する。

## 10. 明示的な未決定・検証事項
1. 10/30/40人の日勤・夜勤・リーダー必要数と、能力・夜勤不可・曜日固定休の厳密な配分。人数比率の丸めと成立性検証。
2. 固定年月と月またぎの夜勤・明け・休日の境界条件。
3. B/C/Dの具体的な希望休・固定セル数、衝突率、seed。
4. 制約独立評価の全ルールと公平性・能力偏差の正確な式。
5. API内部計測の取得方式と本番互換性、CPU/メモリ計測方法。
6. DBの詳細カラムと、エラー・issues/元シフト保存形式。
7. 比較許容条件・統計判定の閾値。

これらは未決定のまま**最小プロトタイプの開発を妨げない**。暫定値を採用したときは明示する。
